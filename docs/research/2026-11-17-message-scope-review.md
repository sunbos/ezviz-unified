## 独立离线签名核对（算术核对，非平台实测）

对 5130 的展示材料做了离线向量算术核对：element574 展示正文、element577 key、element580 `t`、element583 方程签名、element586 HTTP 示例。

- `HMAC-SHA1(key, (body + t).encode)` 对三种 body 取法逐一核算：展示正文原字节 → false；去外层换行 → false；HTTP 示例展示 body → false。
- `json.loads(展示正文)` 后 `json.dumps(ensure_ascii=False, separators=(',',':'))` 得到的 minified 派生字节 → **true**；HTTP 示例的 `Signature`/`t` 与方程示例一致。

结论只能表述为：**对 5130 展示示例，minified 派生字节的离线向量匹配**。官方展示字节本身仍存在矛盾（按原字节验不过）。因此线上接收必须对**原始收到的 bytes** 验签，不得先 parse/minify 再验。这同时确认 `src/ezviz_unified/webhooks.py` “raw bytes 直接拼接、不重序列化”的取向是正确的；但也意味着官方示例不能作为线上行为已核定的证据。

注意不能把“旧六篇未查到示例”继续泛化为“全部文档都无示例”——5128 已有官方 quickstart、5130 已有签名展示；海外 `t` 单位仍未核定。

## 建议架构（设计选择，尚未实现）

定位：保留 SDK 纯函数 helpers；新增**仓库级独立接收示例**（非 SDK runtime、非托管服务）。

- 形态：loopback 默认、固定 POST 路径、显式独立 secret；有界 body 大小、连接数、运行时长、接收次数。
- 流程：读原始 bytes → 验签 → 解析 → 明确定义受理 → 返回 HTTP 200 + `messageId`。
- 缺/坏签名、非法 JSON、超限一律固定错误响应，且不记录原文。
- 有界 `messageId` 去重：成功重复投递仍 ACK 但不重复处理；“同 ID 不同 body”的判据待冻结。
- 不承诺跨重启去重，不承诺 exactly-once。
- 国内 profile 可显式毫秒时窗校验；容错窗口、去重缓存容量等设计数值尚未冻结，不能编造；海外不猜时间单位。
- 安全回执仅含固定枚举/数量/时延/代码来源版本，不含 secret、messageId、设备、body、媒体 URL。
- 明确不做：公网托管服务、自动隧道、代开通平台服务、下载媒体、设备联动。

## 建议验收分层

- 本地离线：helper 向量、去重、有界限制、错误分类——可先行，但不代替平台验收。
- 平台模拟：控制台消息测试可用，但须单独标注，不冒充真实设备事件链（5129 element194–226）。
